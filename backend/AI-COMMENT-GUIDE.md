# AI 通用代码注释指南

## 1. 目标

这份文件用于指导 AI 在阅读和修改代码时写出可维护、与代码强相关的注释。

注释不是代码翻译，也不是功能宣传。一条有效注释应当记录代码背后的决策：

- 业务上为什么必须这样做。
- 如果破坏这个约束，会产生什么错误。
- 代码通过什么具体机制保证这个约束。

AI 不得为了增加注释数量而写空泛说明。优先保证注释准确、相关、可验证。

## 2. 核心标准

### 2.1 业务与代码各占一半

行内注释通常要同时包含两部分：

1. 业务意图：规则、边界、风险、权限或一致性要求。
2. 代码手段：状态检查、字段、SQL、锁、事务、分支、重试、缓存或事件机制。

推荐结构：

```text
业务原因或规则 + 冒号/分号 + 代码如何保证它
```

通用示例：

```text
// 同一资源只能提交一次：先锁记录再检查状态，保证并发请求只产生一个有效结果。
```

```text
// 金额必须在入账前限制上限：这里先校验请求值，数据库更新再用条件语句兜底。
```

只写业务、不写代码落点，容易变成口号：

```text
// 保证数据安全。
```

只写代码动作、不写业务原因，容易变成代码翻译：

```text
// 调用校验方法。
```

### 2.2 注释必须贴着决策点

注释应放在以下位置附近：

- 状态转换之前。
- 权限或归属判断之前。
- 金额、数量、时间边界计算之前。
- 加锁、事务、条件更新之前。
- 幂等、重试、补偿和降级分支之前。
- 外部依赖调用和失败处理之前。
- 数据脱敏、隐私过滤和审计记录之前。
- 不直观的排序、索引、分页或缓存策略之前。

不要把所有解释集中写在类顶部。类顶部只回答“这个类负责什么”。

## 3. 注释层级

### 3.1 类注释

类或接口顶部最多使用一句话说明职责。

推荐：

```text
/** 用户身份校验和会话凭据管理。 */
```

```text
/** 将支付结果写入订单和资金流水。 */
```

禁止：

- 罗列类中所有方法。
- 写长篇设计说明。
- 重复添加作者、版本、创建日期等模板。
- 使用“这是一个服务类”这类没有信息量的描述。

### 3.2 方法注释

方法名、参数和返回类型已经表达清楚时，不强制写 Javadoc。

只有存在以下情况时才写方法注释：

- 调用方必须满足某个前置条件。
- 方法有明显副作用。
- 方法会抛出不直观的业务异常。
- 操作涉及事务、锁、幂等、重试或外部依赖。
- 返回值可能经过降级或聚合。

方法注释保持一到两句话，重点说明契约，不重复实现步骤。

### 3.3 字段注释

只在以下情况添加字段注释：

- 单位不直观，例如金额、毫秒、字节。
- 使用枚举编码或状态值。
- 字段有精度、范围、时区或空值约束。
- 字段存在历史兼容含义。

简单名称已经说明含义的字段不需要注释。

### 3.4 行内注释

行内注释用于记录实现过程中的关键决策，通常使用单行注释。

一项重要规则只解释一次，不要在同一方法内反复描述同一机制。

## 4. 应当写注释的场景

### 4.1 状态机

说明为什么只允许特定状态进入下一步，以及代码如何阻止非法状态。

```text
// 只有已支付订单可以发货：状态检查与物流记录在同一事务中完成，避免未付款先出库。
```

### 4.2 资金与数量

说明金额或数量的来源、精度、上限、守恒关系和更新方式。

```text
// 余额判断和扣减必须在同一条条件更新中完成；影响行数为零表示余额不足，不能继续写成功记录。
```

### 4.3 并发与锁

说明锁保护的业务不变量、加锁对象和锁顺序。

```text
// 两个账户按固定标识顺序加锁，避免相反方向的并发转账互相等待。
```

### 4.4 幂等与重试

说明重复请求的业务后果，以及幂等键或唯一约束如何收敛并发。

```text
// 同一幂等键只能完成一次扣款：唯一索引负责抢占，重复请求直接返回首次结果。
```

### 4.5 事务边界

说明哪些数据必须同时提交或回滚，以及为什么不能提前产生副作用。

```text
// 订单状态和事件记录必须同事务写入；外部通知只能在提交后发送，避免通知成功但数据回滚。
```

### 4.6 权限与数据隔离

说明用户能访问什么、资源归属如何校验，以及越权时返回什么语义。

```text
// 详情接口必须校验资源所有者：公开查询和私有详情不能复用同一权限路径。
```

### 4.7 时间与超时

说明时间边界、时钟来源、超时后的状态和补偿方式。

```text
// 超时判断使用数据库时间；不同实例的本地时钟不能决定同一任务是否到期。
```

### 4.8 外部依赖与降级

说明外部依赖失败时业务是否继续、回退到什么路径、由谁补偿。

```text
// 搜索增强服务失败时保留基础查询结果，不能因为非核心依赖不可用阻断主流程。
```

### 4.9 复杂查询和索引

说明过滤条件、排序、索引选择、分页方式以及不能简化的原因。

```text
// 使用游标而不是偏移量：数据持续插入时，偏移分页会出现重复或漏项。
```

### 4.10 数据安全与隐私

说明敏感数据为何不能记录、返回或发送给外部系统，以及代码在哪里限制。

```text
// 日志只记录任务标识，不输出请求正文；正文可能包含用户隐私和凭据。
```

## 5. 不应写注释的场景

不要注释以下内容：

- 简单的变量赋值。
- getter、setter、构造器和显而易见的 CRUD。
- 逐行解释 `if`、`for`、`return` 在做什么。
- 类名和方法名已经完整表达的动作。
- 只写“校验参数”“调用服务”“返回结果”的流程描述。
- 与当前实现不一致的历史说明。
- 被注释掉的废弃代码。
- 没有负责人、原因和完成条件的 TODO。
- 为了凑注释比例而重复表达的内容。

## 6. 表达规则

### 6.1 使用业务语言和代码语言

优先使用代码中真实存在的领域名词、字段名、状态名和动作名。

不要发明代码中不存在的规则。

如果无法确认业务含义：

1. 先阅读相邻代码、接口契约和数据结构。
2. 仍无法确认时，只描述能够证明的技术约束。
3. 不得编造业务背景。

### 6.2 一条注释只表达一个决策

一条注释可以包含两个短句，但不要塞入多个无关主题。

推荐：

```text
// 任务在事务提交后投递：工作线程此刻才能读到完整任务记录。
```

不推荐：

```text
// 这里创建任务、记录指标、提交事务、调用线程池，然后处理异常并更新状态。
```

后一种写法只是复述代码步骤。

### 6.3 保持简洁

- 行内注释通常一到两句话。
- 优先解释原因和保证方式，不展开完整设计文档。
- 同一业务规则在多处使用时，在核心实现处解释一次。

### 6.4 注释必须与代码同步

修改状态、金额、权限、事务、重试或查询条件时，同步检查附近注释是否仍然成立。

过期注释比没有注释更危险。

## 7. AI 执行流程

AI 在写注释前按以下步骤执行：

1. 阅读目标代码及直接调用方和被调用方。
2. 找出业务不变量、失败后果和代码保证机制。
3. 选择真正需要解释的决策点。
4. 在该决策点旁写一条“业务 + 代码”注释。
5. 检查注释是否只是重复代码。
6. 检查注释中的字段名、状态名、方法和行为是否真实存在。
7. 检查是否与同文件其他注释重复。

AI 修改整个文件或模块时，应同时清理：

- 空泛注释。
- 与实现不一致的注释。
- 模板化作者和版本头。
- 重复解释同一机制的注释。

## 8. 注释数量参考

不设强制百分比。

使用以下启发式规则：

- 简单数据载体：通常只需要一句类注释。
- 普通查询或映射代码：只在过滤、排序、索引和异常语义不明显时注释。
- 业务决策密集的代码：通常每 8 至 15 行会出现一个值得解释的判断点。
- 资金、权限、并发和状态转换：优先增加注释，而不是节省注释。

如果一段代码删除注释后仍然不会有人改错，通常不需要注释。

## 9. 自检清单

提交注释前逐项检查：

- 类顶是否只有一句职责说明。
- 注释是否紧贴被解释的代码。
- 是否同时说明了业务原因和代码手段。
- 是否使用了真实存在的字段、状态和方法。
- 是否避免逐行复述代码。
- 是否避免作者、版本和日期模板。
- 是否没有编造无法证明的业务规则。
- 同一规则是否没有被重复解释多次。
- 简单代码是否没有被过度注释。
- 注释修改后是否仍与代码行为一致。

## 10. 验收标准

一条合格注释应让读者能够回答：

1. 这段代码保护了什么业务规则。
2. 如果不这样写，会发生什么问题。
3. 当前代码通过什么机制保证该规则。
4. 修改这段代码时最容易破坏什么。

无法回答以上问题的注释，应删除或重写。
